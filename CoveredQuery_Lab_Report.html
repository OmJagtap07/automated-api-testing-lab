❓ Why is this query NOT covered?
Although the query uses an index on email, the projection requests username — a field that is not part of the index. MongoDB must therefore perform a FETCH stage to retrieve the full document from disk to resolve the projected field, making this an uncovered query. Additionally, _id is implicitly included in projections unless explicitly excluded, and it is not stored in this single-field index.

🟢 Step 3 — Covered Query (Compound Index)

Compound Index Created

db.users.createIndex({ email: 1, username: 1 })

Modified Query (Covered)

db.users.find(
  { email: "user00000@gmail.com" },
  { username: 1, _id: 0 }      ← _id explicitly excluded
).explain("executionStats")

→

  "inputStage": {

    "keyPattern": { "email": 1, "username": 1 },
    "indexName": "email_1_username_1",
    "direction": "forward",
    "indexBounds": {
      "email": ["[\"user00000@gmail.com\", \"user00000@gmail.com\"]"],
      "username": ["[MinKey, MaxKey]"]
    },

    "seeks": 1

✅ Why is this query covered?
The compound index { email: 1, username: 1 } stores both the filter field (email) and the projected field (username) in the index itself. By also explicitly excluding _id (which is not in the index), MongoDB can satisfy the entire query — filter, fetch, and projection — using only the index B-tree, without touching a single document on disk. This is confirmed by PROJECTION_COVERED and totalDocsExamined: 0.

📝 Written Explanations

1. Why the first query is not covered

The first query uses a single-field index on email. While MongoDB can use the index to locate the matching key quickly (IXSCAN), it still needs to load the full document from disk (FETCH) to retrieve the username field, because username is not stored in the index. The implicit inclusion of _id also contributes — since _id is not in the index, MongoDB cannot resolve it without a document fetch.

2. Why the second query is covered

The second query creates a compound index { email: 1, username: 1 } that contains all the fields needed — the filter field (email) and the projected field (username). MongoDB can resolve the entire query operation (filter + projection) using only the index entries in memory, with zero disk reads. The explain plan confirms this with the PROJECTION_COVERED stage and totalDocsExamined: 0.

3. Why excluding _id is necessary

MongoDB includes _id in query results by default. Since _id is not stored in our compound index { email: 1, username: 1 }, including it would force MongoDB to perform a FETCH stage to read the document from disk, breaking the covered query. By explicitly setting _id: 0 in the projection, we ensure that every field in the result set is available directly from the index, enabling a truly covered query.

4. How performance improved

The covered query eliminates disk I/O entirely for this lookup — totalDocsExamined dropped from 1 → 0. At scale (10,000+ documents on a busy server), this translates directly into lower latency, reduced I/O pressure, lower CPU usage, and more efficient WiredTiger cache utilization. In a high-traffic application with millions of such queries per day, a covered query can mean the difference between requiring a single index server vs multiple document storage servers — index-only access is dramatically faster as no page faults or storage engine reads occur.
